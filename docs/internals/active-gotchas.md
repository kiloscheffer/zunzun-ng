# Active gotchas

Operational rules-of-thumb — situational notes important enough to keep grep-able, grouped by area of the codebase. Read the matching section before touching that area. Each bullet captures one rule, one tripping-hazard, or one footgun that has burned someone (or would burn the next person).

## Environment and venv

- `.venv/` must be excluded from cloud-sync clients (Dropbox, OneDrive, iCloud). uv's default hardlink mode on Windows shares inodes between `.venv/` and the global uv cache (`%LOCALAPPDATA%\uv\cache\`); a sync client watching `.venv/` doubles the storage and breaks the hardlink relationship on cross-machine sync, silently corrupting Python imports (manifests as OS error 396 or hard-to-trace `ImportError`s). With the exclusion in place, no special handling is needed (verified 2026-04-28). Workaround if the exclusion isn't possible: prefix `uv` commands with `UV_LINK_MODE=copy`.
- Cold-cache smoke flakiness. The first smoke run after `rm -rf .venv && uv sync` (especially after a pyeq3 reinstall) can time out on 3D scenarios because spawn workers compile `.pyc` files on first import. Re-running on the warm venv passes.
- `rm -rf .venv` may fail with "Device or resource busy" on Windows when transient background processes (Dropbox indexers, Windows Search, etc.) hold handles open momentarily. PowerShell's `Remove-Item .venv -Recurse -Force` uses native Win32 calls and handles these gracefully where bash's `rm -rf` (via MSYS POSIX-emulation) does not.
- Avoid running pytest + smoke in parallel right after a `uv lock` that changed any source URL — they'll race for cache locks.

## Spawn LRP pattern

- Never call `os.getloadavg`, `/proc`, `vmstat`, or `os.popen` directly from view or LRP code. Extend `zunzun/platform_compat.py` instead — it shims the platform-specific calls (Linux uses real loadavg; Windows synthesises one from psutil).
- `os.fork()` and `os._exit()` no longer appear in the codebase. Adding them will break Windows compatibility; prefer `multiprocessing.Process(spawn)` and plain `return` respectively. The `fork-pattern-reviewer` subagent audits for accidental regressions.
- Per-fit worker count is resolved by `zunzun.parallel_pool.resolve_max_workers()`: explicit arg > `ZUNZUN_MAX_WORKERS` env > `settings.MAX_PARALLEL_WORKERS` > auto-detect `min(cpu_count, available_RAM_KiB / 200_000)`. Result is always clamped to the hardware ceiling. Modern Python 3.14 + numpy 2.4 + scipy 1.17 workers use ~140 MB RSS each (down from the original 750 MB pessimistic estimate that drove an old 4-worker hard cap, removed 2026-05-28). On a low-RAM box, set `ZUNZUN_MAX_WORKERS=4` as an emergency throttle. `platform_compat.get_parallel_process_count()` delegates here and additionally throttles down under high system load (load1 > cpu_count + 0.5/1.0/1.5 → reduces to 3/2/1).
- `FitPool` lifetime is per-LRP-child, not per-Django-request. Create instances inside `PerformAllWork()` (which runs in the spawned LRP child), NOT in `__init__()` (which runs in the Django request handler before spawn — the parent's `multiprocessing.Process(spawn)` snapshot doesn't pickle a live `ProcessPoolExecutor`). Tear down in `PerformAllWork()`'s `finally` block. `CheckIfStillUsed()` tears down — via the shared `_teardown_abandoned_fit()` helper, which calls `self.fit_pool.shutdown(wait=False, cancel_futures=True)` and `terminate()`s live workers — on ANY of three abandonment signals: a foreign `process_id` in the row, a stale (>300 s) heartbeat, OR a **missing row** (`get_status("process_id") is None`). The missing-row case means the housekeeping age-sweep deleted this row; the child MUST tear down rather than early-return, because once the row is gone the orphaned child can no longer observe the other two signals, so a CPU-heavy fit would otherwise keep saturating cores until it finishes on its own.
- `FitPool.__init__` injects `OMP_NUM_THREADS / OPENBLAS_NUM_THREADS / MKL_NUM_THREADS=1` via `os.environ` (using "treat empty string as unset" semantics, not `setdefault`) before creating the executor. Spawn workers inherit these and use single-threaded BLAS — parallelism comes from the worker count, not from BLAS threads. Without this, 22 concurrent workers × 22 BLAS threads each → OpenBLAS init memory bomb on big-core Windows boxes (`OpenBLAS error: Memory allocation still failed after 10 retries` → `BrokenProcessPool`). Power users wanting BLAS threading inside one worker can set `OMP_NUM_THREADS=8` in their shell explicitly; FitPool only fills in empty/unset values.
- Inner parallel phases (`FunctionFinder.PerformWorkInParallel`, `CreateOutputReportsInParallelUsingProcessPool`, `StatisticalDistributions.PerformWorkInParallel`) all submit to the same `self.fit_pool` (inherited from `StatusMonitoredLongRunningProcessPage`). Worker reuse across phases amortizes the ~2 s spawn-import cost over the entire fit. On `BrokenProcessPool`, raise `_ReportsPipelineAborted` (sentinel exception in `StatusMonitoredLongRunningProcessPage`) — caught by `PerformAllWork`'s try/finally so the subsequent PDF/HTML stages are skipped and the user-visible error status survives, rather than the pipeline silently continuing to a broken empty results page.

## Sessions and state

- Every session write goes through `save_with_retry(session)` from `zunzun/session_helpers.py`; every session read goes through `load_with_retry(session, key, default=None)` from the same module. Both wrap the 100-retry @ 10Hz loop that handles SQLite contention from concurrent spawn children. Direct `session.save()` or `session[key]` calls in spawn-child code are a bug. Spawn children open fresh DB connections (vs. fork's inherited ones), so lock contention is arguably more relevant post-migration, not less.
- Session values are stored as JSON via `NumpySessionSerializer` (wired in `settings.SESSION_SERIALIZER`, defined in `zunzun/session_helpers.py`). numpy scalars and arrays produced by pyeq3 are coerced to plain Python primitives automatically at `session.save()` time — callers do NOT need to cast manually (the old `_json_native` per-call-site helper was removed once the serializer landed). Anything else stored must still be JSON-encodable (no sets, datetimes, live scipy objects, etc.).
- **Status store is a per-dispatch ORM row, not a session blob.** `LRPStatus` (`zunzun/models.py`, table `zunzun_lrpstatus`) holds `current_status`, `start_time`, `last_status_check`, `redirect_to_results`, `parallel_count`, `process_id`, and `state`; the autopk `id` is the dispatch identity. The current dispatch's row pk is stored in `request.session["lrp_status_pk"]`. Status writes go through `update_status(**fields)` on `StatusMonitoredLongRunningProcessPage` — an unconditional single-row `LRPStatus.objects.filter(pk=...).update(...)`. Reads go through `get_status(field, default=None)`. There is no ownership check: each fit child writes only its own row. The old apparatus (`_we_own_status_slot`, `_publish_terminal_error`, `dispatched_at`) has been deleted. `migrate` now creates the `zunzun_lrpstatus` table in addition to `django_session` — no extra command, but operators should know this app table exists.
- **`LRPStatus` lifecycle is an explicit `state` field, not derived fields.** `LRPStatus.State` is a `TextChoices` enum with three values: `INITIALIZING` (default, row just created), `RUNNING` (child claimed the row), and `TERMINAL` (fit finished — success, abort, or error). Lifecycle transitions go through two classmethods on `LRPStatus`: `mark_running(pk, pid)` (INITIALIZING → RUNNING, sets `process_id`); `mark_terminal(pk, *, redirect=None, current_status=None, parallel_count=None)` (→ TERMINAL, always sets `state=TERMINAL` + `process_id=0` atomically so the terminal tuple can never be set partially; optional fields only written when passed so a bare `mark_terminal(pk)` never clobbers a redirect a prior stage already published). The per-user gate in `LongRunningProcessView` reads `state` directly: `state == RUNNING` + `process_id > 0` + heartbeat within 300s = active; `state == INITIALIZING` + `start_time` within 60s = pending. `StatusView` and `StatusUpdateView` key terminal detection on `state == TERMINAL`. Do NOT key terminal detection off `redirect_to_results` alone — a mid-fit crash whose error page could not be written leaves a terminal row with an empty `redirect_to_results`, so a redirect-only check would mistake it for "not yet done". The durable terminal signal is `state == TERMINAL`. Note `redirect_to_results` is NOT cleared on serve: on completion `StatusView` redirects the owner to `/Results/<token>/`, and `ResultsView` reads `redirect_to_results` directly without clearing it, so the shareable result link stays idempotent across refreshes.
- **`PerformAllWork`'s `finally` stays non-terminal by design.** The `finally` block in `StatusMonitoredLongRunningProcessPage.PerformAllWork` only calls `self.update_status(process_id=0)` — it deliberately does NOT set `state=TERMINAL`. On the unhandled-exception path the exception propagates to `_run_fit_child`'s `except` handler, which writes a terminal error artifact and calls `LRPStatus.mark_terminal(...)` to publish the error redirect. If `finally` pre-set `state=TERMINAL`, that handler's guard (`current_state == TERMINAL` → don't clobber) would skip the error redirect and orphan the artifact. So `state=TERMINAL` is set only by real terminal writers: the success path at the end of the `try` block (`self.mark_terminal()`), the abort sites inside `_ReportsPipelineAborted` handlers, or `_run_fit_child`'s exception handler.
- **`_finalize_row_if_child_dead` is the reader-side backstop.** A fit child that vanished without setting `state=TERMINAL` (SIGKILL / OOM / crash, or a failed terminal write) leaves `process_id` set and `state` non-terminal — the poll loop would run forever. `StatusView` and `StatusUpdateView` both call `_finalize_row_if_child_dead(row)` which checks `pid_is_alive(row.process_id)`; if the pid is gone, it calls `LRPStatus.mark_terminal(row.pk)` so the next poll cycle ends cleanly.
- **Data and functionfinder stores are per-dispatch ORM rows, not session blobs.** Each dispatch gets an `LRPDispatchData` row (`zunzun/models.py`, table `zunzun_lrpdispatchdata`) — a OneToOne to `LRPStatus` with `on_delete=CASCADE` so deleting the status row atomically drops its data. The two JSON fields, `data` and `functionfinder`, use `encoder=NumpyJSONEncoder`. Reads and writes go through `zunzun/dispatch_data.py`: `save_items(status_pk, field, items)` and `load_item(status_pk, field, key, default=None)`, keyed by the dispatch's `LRPStatus` pk (`status_row_pk`). `LongRunningProcessView` pre-creates the `LRPDispatchData` row in the PARENT before the child spawns to avoid a `get_or_create` race. `SaveDictionaryOfItemsToSessionStore` and `LoadItemFromSessionStore` in `StatusMonitoredLongRunningProcessPage` delegate to these helpers — callers use the same named interface as before, the storage is now ORM not SessionStore. The old `session_key_data` / `session_key_functionfinder` keys and their `SessionStore` objects are gone.
- **Cross-dispatch reads use `data_source_pk` (the read source) vs `status_row_pk` (the write target).** A dispatch that must READ a *prior* dispatch's `data`/`functionfinder` store sets `self.data_source_pk` to that prior row's pk. The base `StatusMonitoredLongRunningProcessPage.LoadItemFromSessionStore` resolves the read pk via `_data_read_pk()` — returns `data_source_pk` when set, else falls back to `status_row_pk`. `SaveDictionaryOfItemsToSessionStore` and all status writes (`update_status`, `get_status`, `mark_*`) always key off `status_row_pk`; only reads honor `data_source_pk`. Two flows set it: `FunctionFinderResults` (reads the ranking run's ranked list + dataset; set by the view dispatcher before `TransferFormDataToDataObject`), and the `/FitEquation` RANK interface-GET pre-fill (`views.py`, render-only — leaves `status_row_pk` unset so a stray status write no-ops). The pk is carried to the child via the typed `ChildPayload.data_source_pk` field. There is NO per-subclass `LoadItemFromSessionStore` override and NO `extra["ranking_status_pk"]` bag key anymore — reads are data-driven, so the base method tells the whole truth. (`ranking_token` is unrelated: it is the ranking's shareable capability token threaded into results-page nav links, not a read-source pk.)
- **FunctionFinder ranking identity travels as `&ranking=<result_token>` in results URLs, NOT as a session key.** As of `feat/functionfinder-token-binding` (2026-06-02), the old `session["functionfinder_ranking_pk"]` slot is gone; ranking identity is the `LRPStatus.result_token` of the ranking dispatch, appended to every results-page and "fit this equation" URL. `zunzun/views.py:_ranking_pk_from_token` resolves the token back to a `status_row_pk` for `FunctionFinderResults`. The `FunctionFinderResults` GET also sets `cookie_test` for token-bearing recipients so a cross-session visitor (no ranking cookie) passes the pre-fit gate and can render the result. Shared FF links are disk-bounded: as of `feat/ff-link-retention` (2026-06-02) the ranking's `LRPStatus` row is retained by a `temp/ffanchor_<pk>` marker (see the `ffanchor_<pk>` bullet under "Filename grammar in temp/" below), so a shared link lives as long as a file-backed result rather than expiring at `SESSION_COOKIE_AGE`.
- **Private status addressing vs. shareable result addressing.** Status pages use pk-based URLs — `/StatusAndResults/<pk>/` (served by `StatusView`) and `/StatusUpdate/<pk>/` (served by `StatusUpdateView`) — gated by `_load_owned_status_row`, which returns None for both "row not found" and "row belongs to a different session" to avoid leaking pk existence as an enumeration oracle. The bare `/StatusAndResults/` URL is a back-compat `StatusRedirectView` that forwards to the session's newest non-terminal owned row. Result pages use capability tokens — `/Results/<token>/` (served by `ResultsView`) and `/EvaluateAtAPoint/<token>/` — with no cookie check; possession of the `result_token` (auto-minted via `default=secrets.token_urlsafe`, the bare callable Django invokes with no args on every `LRPStatus` row) grants access. On completion, `StatusView` redirects the owner from `/StatusAndResults/<pk>/` to `/Results/<token>/`.
- **Concurrency caps: `MAX_CONCURRENT_FITS_PER_SESSION` and `MAX_CONCURRENT_FITS_PER_IP`.** Both settings live in `settings.py` with DEBUG-aware defaults via `_fits_default` (under `runserver`/dev both relax to 10; under any non-runserver server — Waitress/WSGI/smoke/pytest — they are 1 and 4 respectively) and are env-overridable via `ZUNZUN_MAX_CONCURRENT_FITS_PER_SESSION` / `ZUNZUN_MAX_CONCURRENT_FITS_PER_IP`. The gate in `LongRunningProcessView` calls `_active_fit_counts(session_key, ip)` which counts non-TERMINAL rows (`state != TERMINAL`) whose `last_status_check >= now-300s`, grouped by `owner_session_key` and `owner_ip`; INITIALIZING and RUNNING rows are counted alike if their heartbeat is fresh — there is no `process_id` filter. Over either cap it probes-and-releases provably-dead rows (via `_finalize_row_if_child_dead`) then recounts; over the cap after the probe, it returns an HTTP 200 with an explanatory message. Fail-open on transient DB errors (`OperationalError`/`InterfaceError`) — logged at WARNING — and re-raises on non-transient errors (logged at ERROR) so a structural bug is not silently swallowed. The old `ALLOW_MULTIPLE_CONCURRENT_FITS_PER_USER` boolean is removed — it was a breaking-change flag whose `True` mode (unlimited concurrent fits per session) was the problematic default; the new per-session cap default of 1 matches the old `False` mode and is the safe default.

## Templates and URLs

- `/CommonProblems/` is a case-sensitive CapitalCase URL; the on-disk directory is lowercase (`commonproblems/`). The bare trailing-slash URL `/CommonProblems/` is explicitly routed to serve `index.html` because Django's `static()` helper doesn't auto-index.
- The coefficient-picker `<td>` cells in `templates/zunzun/divs/polyfunctional_selection_div.html` / `polyrational_selection_div.html` / `polynomial_customization_div.html` are JS-coupled, but via modern, explicit hooks (the legacy `document.all`/`document.layers`/`.style.backgroundColor` pathway is gone). Selection *state* lives in the `selected` CSS class (`isSelected`/`setSelected` in `JavascriptCommonToFunctionMatrices.js` are the only read/write points). Each cell's `data-flag` attribute names its paired hidden `<input>`; `setSelected` writes that input on every toggle, and the input's *initial* value is server-rendered from the `selected` bool — so the form is correct at rest (no submit-time sweep). Cell `id` (`CPX...`) is still read by the per-matrix preview builders. Do not change a cell's `id`, `data-flag`, or the `selected`-class protocol without updating the matching JS.

## Files and directories

- `static/` (committed assets) and `temp/` (runtime outputs) serve two separate URL prefixes — `STATIC_URL = '/static/'` vs `MEDIA_URL = '/temp/'`. For Python-side paths use `settings.STATIC_FILES_DIR` and `settings.TEMP_FILES_DIR` respectively. They are different paths since the 2026-04-28 static-files restructure; before that, both lived under `temp/`.
- `temp/` is auto-trimmed by `HomePageView`'s housekeeping when total size exceeds `MAX_TEMP_DIR_SIZE_IN_MBYTES` (default 500).
- LRP trace logging routes through `logging.getLogger("zunzun.LongRunningProcess.*")`. Default level is `WARNING` (silent). To enable per-step tracing in spawn children, set `ZUNZUN_LRP_LOG_LEVEL=DEBUG` — output flows into `temp/{pid}.log` because `_setup_child_root_logging()` at the top of `_run_fit_child` installs the per-pid `FileHandler` on the root logger BEFORE any `PerformAllWork` code runs. `FitPool` workers are sub-children of the LRP child and DO NOT inherit its handlers (each is its own fresh spawn); `FitPool.__init__` wraps any caller-supplied initializer in `_worker_initializer` so the same per-worker-pid FileHandler installs before any worker code runs — without this, `logging.exception` calls in the `ParallelWorker_*` / `parallelWorkFunction` / animation classes would fall back to stderr and the user-facing "see log file" message would point at a missing file. Parent-side trace messages (e.g. from `SetInitialStatusDataIntoSessionVariables`) are not routed by default — add a handler to `settings.LOGGING` or run with `runserver --verbosity` to see them. The old `pid_trace.py` shim (dormant-by-design `return`-at-top no-op) was removed when the per-LRP logger landed; bare positional `pid_trace.pid_trace()` markers were deleted (no useful message), text-bearing ones converted to `_logger.debug(...)`.

## Filename grammar in temp/

- Artifact filenames follow `zun_<pid_b36_4>_<ms_b36_8>_<anchor_3>_<rank_2>.{ext}` (per-component) or `zun_<pid_b36_4>_<ms_b36_8>_zun_00.{ext}` (page-level). Helpers live in `zunzun/LongRunningProcess/_unique.py`: `new_unique_string()`, `page_artifact_filename/path/url()`, and the `b36()` formatter.
- Anchor namespace reservations: `zun` is the page-level anchor (PDF, result HTML); `h` prefix is reserved for parametrized histogram instances (`StatisticalDistributionHistogram` uses `h` + 2-char base36 of `distributionIndex`). No other anchor may start with `zun` or `h`.
- `b36()` never truncates: values too large for the requested width produce a longer string. Rank field is sized for 0..1295 (FunctionFinder cap ~1k); larger values produce 3+ char suffixes and break fixed-width sortability for those rows specifically — accepted trade-off.
- `ffanchor_<pk>` files are FunctionFinder ranking retention anchors (not artifacts — they sit outside the `zun_<...>` grammar). A ranking row's `redirect_to_results` is a `/FunctionFinderResults/` URL, not a `temp/` file, so it has no natural disk anchor; the marker gives it one. `_sweep_aged_rows` excludes ranking rows (URL contains `/FunctionFinderResults/`); `_sweep_orphaned_terminal_rows` reaps a ranking row once its `ffanchor_<pk>` marker is size-pruned. Helpers: `ff_anchor_path` / `write_ff_anchor` / `touch_ff_anchor` in `zunzun/LongRunningProcess/_unique.py`. Don't delete these markers out of band — that reaps the shareable `/Results/<token>/` link early. **Safety net:** the marker is tiny and the ranking's payload lives in `LRPDispatchData` (DB, NOT counted toward `MAX_TEMP_DIR_SIZE_IN_MBYTES`), so an FF-heavy / low-artifact workload could keep `temp/` under quota forever and never evict the marker — `_sweep_aged_rows` therefore also applies a hard age ceiling (`settings.FF_RANKING_MAX_AGE`, default 90d, env `ZUNZUN_FF_RANKING_MAX_AGE_SECONDS`) that reaps FF ranking rows past it regardless of the marker, bounding row/DB growth.

## FunkLoad legacy

- FunkLoad is not in `pyproject.toml`. Its `setup.py` uses `ez_setup`, which was removed from modern setuptools, so it can't be installed under the uv-managed Python 3.14 environment.
- Its assertion strings in `funkload_tests/test_Simple.py` are also stale under modern numpy/scipy/pyeq3. The folder is preserved as historical reference; do not invest in re-running it. Port individual assertions to pytest or to the smoke script if needed.

## Deploy

- `settings.py` ships with empty placeholders for `SECRET_KEY`, `EXCEPTION_EMAIL_ADDRESS`, `EMAIL_HOST_USER`, and `EMAIL_HOST_PASSWORD`. Email sending is gated on these being truthy (see the exception handler in `LongRunningProcessView`), so leaving them blank silently disables email rather than crashing.
- `DEBUG` is toggled automatically by looking for `'runserver'` in `sys.argv` (see `settings.py`), so running under Waitress or WSGI disables debug regardless of env vars.
- Rate limiting is always in effect (no install-time gating). To disable for local testing, set `RATELIMIT_ENABLE = False` in `settings.py`. When a caller exceeds the rate, the `@middleware.rate_limit_sleep` decorator (stacked below `@ratelimit` on each rate-limited view) applies a 5-second `time.sleep` before the view body runs — this specifically breaks polling endpoints (`StatusUpdateView` is intentionally not decorated with `@ratelimit` for this reason).
- Demo mode is off by default. Set `ZUNZUN_DEMO_MODE=1` to turn an instance into a public showcase: it caps fit-runs to `DEMO_MAX_FITS_PER_HOUR` (default 4, env `ZUNZUN_DEMO_MAX_FITS_PER_HOUR`) per IP per hour (hard 429 from `LongRunningProcessView`) and paints a faint diagonal "DEMO" watermark behind page content. The hourly counter lives in the ratelimit cache (default `LocMemCache`), which is **per-process** — on a single-process Waitress box (the documented deployment) it is shared across threads and correct, but if you ever run multiple Waitress processes the effective ceiling becomes N×cap. Configure a shared cache backend (`CACHES` → Redis/memcached/DB) before scaling out.
